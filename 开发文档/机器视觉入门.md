# 第 1 节 一个机器视觉系统到底由什么组成

```
   ┌────────┐   ┌────────┐   ┌────────┐        ┌──────────────┐
   │  光源   │ → │  工件   │ → │  镜头   │ → │   相机       │ → 图像数据 → 软件（HALCON）→ 结果
   └────────┘   └────────┘   └────────┘        └──────────────┘
      打光         被测物        成像            把光变成数字
```

**这条链上，越靠左越重要。** 一句在行业里流传的话：**"打光打好了，算法就成功了一半"**。原因很简单：

- 算法是"在像素上找规律"。如果光和背景没弄好，工件和背景在图像里**几乎一样**，那再厉害的算法也只能瞎猜；
- 反过来，如果工件在图像里和背景**泾渭分明**，那最简单的阈值分割就能搞定。

**我们这个项目的"光"和"场景"是什么样**（很重要，决定了后面所有参数）：

| 条件 | 内容 | 对算法的影响 |
|---|---|---|
| 相机位置 | **固定机位俯拍**（像手机架在固定位置） | 工件出现的位置范围稳定 → 以后加 **ROI**（只在一块区域里找）很容易 |
| 光源 | 自然光 | 会随天气/时间变化 → 所以要**手动定阈值**而不是"每次都自动算"（见第 4 节） |
| 背景 | **白色盘子** | 工件比背景暗 → 阈值分割方向明确（取暗的像素） |
| 工件 | 螺丝（平躺、细长）、螺母（接近方圆） | 形状差别大 → 能用形状特征分类 |

> 💡 **记住这个思路**：遇到任何一个视觉任务，先问"**工件和背景在图像里差在哪**"（亮度差？颜色差？边缘？纹理？），再决定用什么算法。这一步想清楚了，代码往往很短。

# 第 2 节 图像在计算机里到底是什么

## 2.1 像素与灰度

图像就是**一堆数字排成的方阵**。每个数字叫**像素（pixel）**，表示那一小块的**亮度**。

- 我们这个项目的图是 **8 位灰度图**：每个像素取值 **0~255**（0=全黑，255=全白）
- 彩色图有 **3 个通道**（R/G/B），每个通道各一张 0~255 的方阵 → 所以我们第一步常常要 `rgb1_to_gray`（转灰度），因为后面只关心"亮还是暗"

## 2.2 分辨率

`1440×1080` 意思是：**宽 1440 列、高 1080 行**，一共约 155 万个像素。

- 分辨率高 → 看得清细节，但算得慢、文件大
- 口诀：**"零件的最小特征至少要有 3~5 个像素"**，否则它根本"不存在"在图像里

## 2.3 坐标系：行(row) 和 列(col) —— 新手最大的坑

数学课上是 `(x, y)`：x 横向、y 纵向。
**图像处理里反过来讲，而且是"行在前"**：

```
       列 col (x 方向) →
     ┌──────────────────────────┐
  行 │ (0,0)  (0,1)  (0,2) ...  │
 row │ (1,0)  (1,1)  (1,2) ...  │
  ↓  │ (2,0)  (2,1)  (2,2) ...  │
     └──────────────────────────┘
```

- **原点是左上角**（不是左下角）
- **行 = 纵向 = Y**，**列 = 横向 = X**
- HALCON 的算子参数顺序基本都是 `(Row, Column)`（例如 `smallest_rectangle2` 返回 `Row, Column, Phi, ...`）

> ⚠️ 所以我们代码里写 `part.Row` 是"纵向位置"、`part.Col` 是"横向位置"。写反了框就会跑到别处 —— 这是新手最常见的事故。

## 2.4 我们项目里图像长什么样（数据实测）

| 项目 | 实测值 | 说明 |
|---|---|---|
| 尺寸 | 1440×1080 | 三通道彩色 |
| 背景灰度 | 约 150 | 直方图里占比最大的那一档（白盘子） |
| 零件灰度 | 约 60~120 | 金属件比盘子暗 |
| 外圈 | 有一圈更暗的边 | 这是相机视野边缘/台面，不是零件（所以面积上限要设，见 4.5 节） |

# 第 3 节 软件侧：HALCON 是怎么被 C# 调用的

## 3.1 托管壳 与 native 库

```
你的 C# 代码
   ↓ 调用
halcondotnet.dll  （托管壳：一堆 C# 方法，1.5 MB，只是"翻译"）
   ↓ P/Invoke
halcon.dll        （native C++ 库：真正算东西，80 MB）
```

- 壳的版本必须和 native 库版本一致（我们是 24.11.1.1）
- native 库要靠 `PATH` 找到、靠 `HALCONROOT` 找 license → 这就是 `HalconEnvironment.cs` 干的事

## 3.2 数据类型

| HALCON | C# 类型 | 是什么 |
|---|---|---|
| 图像 / 区域 / XLD 轮廓 | `HObject`（子类 `HImage` `HRegion` `HXLD`） | **图标对象**，底层是 native 句柄，必须 `Dispose()` |
| 数字 / 字符串 / 数组 / 句柄 | `HTuple` | 一个"多值容器"：`.I` 取整数、`.D` 取小数、`.S` 取字符串、`[i]` 取第 i 个 |
| 窗口 | `HWindow` | 显示用的窗口（我们用它 disp 图像和框） |

## 3.3 算子的两种写法

同一个算法有两种表达方式，我们混着用：

```csharp
// ① 算子式（贴近 HDevelop，参数顺序固定，输出参数放中间或后面）
HOperatorSet.Threshold(gray, out HObject region, 0, 120);

// ② 面向对象式（对象作为主语，链式调用，可读性好）
HImage img = new HImage("1.jpg");
HRegion r = img.Threshold(0, 120);
```
**"算子"就是一个函数**：输入图像/参数 → 输出图像/区域/数值。HALCON 有 2000 多个算子，我们只用了十几个。

# 第 4 节 检测的完整流程（本项目六步，逐步讲透）

先把骨架摆出来，后面逐步展开：

```
彩色图
  │ ① rgb1_to_gray        转灰度
  ▼
灰度图
  │ ② threshold(0,120)    二值化：暗的像素变白（前景），亮的变黑（背景）
  ▼
二值区域（含高光造成的破洞/碎片）
  │ ③ closing_circle(5)   闭运算：把破洞和小缝补上
  ▼
完整区域
  │ ④ fill_up             填内部孔洞
  ▼
干净区域
  │ ⑤ connection + select_shape(area 2000~60000)   拆成单个零件 + 按面积过滤
  ▼
候选区域（每个对应一个零件）
  │ ⑥ area_center / smallest_rectangle2 / circularity   量位置、形状、朝向
  ▼
特征值 → 分类（长宽比）→ 输出：框、编号、角度、计数
```

## 4.1 第①步 转灰度（rgb1_to_gray）

彩色图三个通道，直接处理太浪费也算得慢。而且我们判断"是不是零件"只看**亮暗**，不需要颜色。
`rgb1_to_gray` 按人眼感受加权平均（绿权重大）：`Gray ≈ 0.299R + 0.587G + 0.114B`。

> **什么时候不能转灰度**：靠颜色区分目标时（例如红色的缺陷、蓝色标签）→ 那时要用 HSV 通道或颜色分类。

## 4.2 第②步 二值化（threshold）—— 视觉里最重要的一步

**目标**：把图像变成"只有前景和背景"两种像素（0 和 255），**也就是把"零件"从背景里切出来**。

```
灰度 200（盘子）  →  0（背景）
灰度  90（零件）  →  255（前景）
```

`threshold(gray, region, 0, 120)` 的意思是：**取灰度值在 0~120 之间的像素**（我们的零件比盘子暗）。

### 阈值怎么定？三种做法

| 做法 | 算子 | 优点 | 缺点 |
|---|---|---|---|
| **手动固定** | `threshold(img, reg, 0, 120)` | 稳定、可控、快 | 需要先知道大概灰度（所以要用数据看） |
| **自动（Otsu 类）** | `binary_threshold(img, reg, 'max_separability', 'dark', out thr)` | 不用自己定 | **直方图不双峰时会切错** |
| **局部自适应** | `dyn_threshold(img, mean_image(img,51,51), reg, 15, 'dark')` | 抗光照不均 | 参数更玄、算得慢 |

### ⭐ 我们项目的实战教训（很重要）

我们一开始用**自动阈值**，结果 **F1 只有 0.270**；换成**手动阈值 120** 后 **F1 = 0.798**。为什么？

**自动阈值（`max_separability`）的原理**：把灰度直方图分成两类，让"类间差异最大、类内差异最小"（这就是 Otsu 的思想）。
它假设**直方图是双峰的**（一堆背景像素 + 一堆目标像素，中间一个低谷）。

但我们的图里：

```
像素数
  │                                   ███  ← 白盘子（背景，约150）占大头
  │                                  ████
  │                    ▓▓▓▓▓  ← 零件（约60~120）
  │        ░░░░░░░░░░░░░░░░░░  ← 零件边缘/暗部/阴影连着背景，中间没有明显的"低谷"
  └───────────────────────────────────────→ 灰度 0    60   120   150   255
```
金属件有**高光**（镜面反射），一部分像素甚至比盘子还亮；边缘又是渐变的。直方图没有干净的双峰，
自动算法算出来的分界点（约 94）**只切走了零件最暗的那部分**，结果一个零件被切成好几块碎片
（1.jpg 里切出了 **386 个连通域**）→ 框又碎又不准。

**结论（也是最值钱的一条经验）**：
> **"自动"不等于"好"。自动阈值只在直方图干净双峰时才灵；工件有反光时，宁可自己看数据定一个固定阈值。**

那"自己定"怎么定得准？**看数据**：把图读进来，统计一下"盘子大概多少灰度、零件大概多少灰度"，
取两者中间偏零件一侧即可。我们取 120，是因为实测扫描下来它 F1 最高（100→0.729、**120→0.798**、140→0.714、160→0.027）。

## 4.3 第③步 形态学（Morphology）—— 修补区域形状

形态学就是"用一个小形状（结构元）去擦区域"。四个基本操作，**记住直觉就够了**：

| 操作 | 直白解释 | 什么时候用 | 副作用 |
|---|---|---|---|
| **腐蚀** erode | 让白色区域**变瘦** | 去掉细小毛刺、断开细连接 | 目标会变小甚至消失 |
| **膨胀** dilate | 让白色区域**变胖** | 连接断开的部分、补小洞 | 目标变大，可能和邻居粘上 |
| **开运算** = 先腐蚀后膨胀 | 先瘦回去再长回来 → **去掉小突起、分离粘连** | 去噪点毛刺 | 细长目标的**两端会被啃掉** |
| **闭运算** = 先膨胀后腐蚀 | 先胖再瘦回去 → **补小洞、连小缝** | 把破碎的目标连成整体 | 太大会把相邻目标**粘成一个** |

HALCON 里对应：`erosion_circle` / `dilation_circle` / `opening_circle` / `closing_circle`（带半径）；也有矩形版本 `*_rectangle1`。

### ⭐ 我们项目的实战教训

**闭运算是救命的**：
```
阈值切出来：  零件被高光切成 3~4 块碎片      闭运算(半径5)后：  连回一个完整零件
   ███  ██   ███         →              ██████████
```
实测：闭运算半径 5 让 F1 从 0.27（不闭运算≈碎片）→ **0.798**。

**但半径不能贪大**：

| 闭运算半径 | F1 | 说明 |
|---|---|---|
| 3 | 0.792 | 还有碎片没连上 |
| **5** | **0.798** | 最优点 |
| 6 | 0.787 | 开始把相邻零件粘一起 → 召回率反而掉 |

**开运算反而有害**（我们早期实测过）：螺丝是细长件，开运算会把它的**两端啃掉**，
进而影响面积和长宽比 → F1 下降。**教科书说"开运算去噪声"，但具体问题要用数据验证。**

## 4.4 第④步 填孔（fill_up）

零件内部可能有小孔（螺母的孔、高光造成的小洞）。这些洞会让：
- 面积算小
- 圆度、长宽比失真

`fill_up` 把区域内部的洞全部填实。注意它只填**被区域包围**的洞，不会把外面的背景填进来。

## 4.5 第⑤步 拆块（connection）+ 面积过滤（select_shape）

**连通域（connected components）**：相邻的白色像素算"一个物体"。
`connection` 就是把一整片白色区域**拆成一个个独立的物体**（每个是一个 region）。

> 连通有两种定义：**4 连通**（只看上下左右）和 **8 连通**（斜着也算连）。
> HALCON 的 `connection` 用的是 **8 连通**。这决定了"斜着搭一点的两个零件算不算一个"。

**为什么要面积过滤**：拆完之后，图里往往有几百个区域，其中大部分是噪声：

```csharp
HOperatorSet.SelectShape(connected, out HObject parts, "area", "and", MinArea, MaxArea);
//                                                                2000      60000
```

| 边界 | 我们的取值 | 为什么 |
|---|---|---|
| 下限 | 2000 px | 比最小的螺母（约 4800）还小一半 → 噪点进不来，真零件不会丢 |
| 上限 | 60000 px | 挡住"整个背景/外圈那一大块"（它可能有几十万像素） |

**面积上下限的取值要按数据来**：我们先统计了标注里零件的面积（螺母 4805~11789、螺丝 11594~22930），再留出余量。

## 4.6 第⑥步 量特征（Feature）—— 把"形状"变成"数字"

分类的前提是**把形状变成数字**。我们用了这几个算子：

| 算子 | 给出的数字 | 物理意义 |
|---|---|---|
| `area_center` | 面积、中心 (Row, Col) | 有多大、在哪 |
| `smallest_rectangle1` | 水平外接矩形的两个角 | **平行于坐标轴**的框（不管零件怎么转） |
| `smallest_rectangle2` | 中心、**角度 Phi**、长边/2、短边/2 | **最小面积外接矩形**（跟着零件转） |
| `circularity` | 圆度 | 1 = 完美圆；正方形约 0.785；越不圆越小 |
| `orientation_region` | 主轴方向 | 区域的"主朝向" |

### ⭐ 为什么分类要用 `smallest_rectangle2`（旋转矩形），不用 `rectangle1`（水平矩形）

```
零件斜着放：            水平外接矩形(rect1)：      最小外接矩形(rect2)：
   ╱╱                      ┌────────────┐            ╱╱
  ╱╱                       │   ╱╱       │         ╱╱
 ╱╱                        │  ╱╱        │      ┌──╱╱──┐
                           └────────────┘      └──────┘
  真实长宽比 2.4            量出来≈1.2（接近方形）   量出来 2.4（真实）
```
**水平框会把斜放的细长零件量成"接近方形"**，那我们用长宽比区分螺丝/螺母就全乱了。
`rect2` 会跟着零件转到最小面积，量出来的才是真实形状，**顺便还给了角度**（我们要输出角度，正好一起拿到）。

## 4.7 分类：把特征变成"结论"

我们只有两类 + 一类"说不准"：

```csharp
if (ratio >= 1.5)      → 螺丝   // 实测螺丝长宽比中位 2.40
else if (ratio <= 1.3) → 螺母   // 实测螺母中位 1.07
else                   → 存疑   // 1.3~1.5 之间不表态，出红框
```

**阈值怎么来的（数据说话）**：我们统计了 40 张图里 166 个螺丝、117 个螺母的形状：

| 特征 | 螺丝 | 螺母 | 结论 |
|---|---|---|---|
| 长宽比 | 中位 **2.40**（10% 分位 1.46） | 中位 **1.07**（90% 分位 1.14） | 分得开 → 阈值放 1.3~1.5 之间 |
| 圆度 | 0.26 | 0.78 | 也能分，作为备用/校验 |

**置信度 = "离判定边界有多远"**：
```csharp
置信度 = 0.5 + 0.5 × (长宽比 - 1.5) / 1.5        // 螺丝这一侧
```
- 刚好卡在阈值上 → 0.5 分（没把握）
- 长宽比 3.0 → 1.0 分（很确定）

为什么这么设计？因为下游（抓取）**宁可得"不确定"，也不要"自信地判错"**。
所以上层可以规定：**有任何一个零件置信度低于阈值，这张图就判 NG**，交给人确认。

**角度为什么要"归一化"**：
- 螺丝是一头一尾对称的 → 转 180° 和原来一样 → 角度只在 `[0,180)` 内有意义
- 螺母是正六边形 → 转 60° 就和原来重合 → 角度只在 `[0,60)` 内有意义

不做归一化的话，同一个姿态会报出好几个"不同角度"，控制抓取时就会把夹爪转错。

## 4.8 输出：把结果画出来

检测结果最终要**给人看**，所以要把框画到图像上：

```csharp
window.SetColor("green");                        // 螺丝绿、螺母蓝、存疑红
window.DispRectangle2(row, col, phi, len/2, wid/2);   // 旋转框
window.SetTposition(...); window.WriteString($"{编号}S {角度}");   // 编号 + 类型 + 角度
```

⚠️ 注意：**框不是画在图像上的**，而是每次显示时"先画图像、再画框"。
这样窗口缩放、翻页时框不会错位（这也是我们把"重画"统一成一个方法的收益）。

# 第 5 节 怎么判断"检测得好不好"—— 评估指标

**这是区分"业余"和"专业"的地方**：不能靠肉眼看"差不多"，要算指标。

## 5.1 四个基本概念

拿"检出结果"和"标准答案（标注）"对比：

| 概念 | 含义 |
|---|---|
| **TP**（真正例） | 检出了，而且确实有（对上了） |
| **FP**（假正例） | 检出了，但那里其实没东西 → **误检** |
| **FN**（假负例） | 那里有东西，但没检出 → **漏检** |
| TN | 没有也没检出（我们这种"找目标"的任务通常不关心它） |

## 5.2 怎么算"对上了"？—— **IoU（交并比）**

框不可能完全重合，需要一个"算不算对上"的标准：

```
        ┌──────────┐
        │  A       │         IoU = 交集面积 / 并集面积
        │    ┌─────┼────┐    · 完全重合 = 1
        └────┼─────┘    │    · 一般取 IoU ≥ 0.5 算"命中"
             │    B     │
             └──────────┘
```

> ⚠️ 我们踩过的坑：一开始我用"**检出框的中心落在标注框里**"当命中标准，
> 结果一个把三个零件粘在一起的大轮廓，中心落在某个框里也**算命中** → 指标虚高。
> 换成 **IoU ≥ 0.5** 之后，粘连、轮廓不准的问题立刻暴露出来（F1 从虚高的 0.88 掉到 0.27，这才是真相）。

**教训**：**评估标准太松，等于自己骗自己。**

## 5.3 三个指标

| 指标 | 公式 | 回答的问题 |
|---|---|---|
| **精确率 P** | TP / (TP + FP) | 我框出来的东西里，有多少是真的？（**别乱框**） |
| **召回率 R** | TP / (TP + FN) | 该检的里面，我检出了多少？（**别漏**） |
| **F1** | 2PR / (P+R) | 两者的综合分 |
| **分类准确率** | 判对的 / 命中的 | 框对上了以后，螺丝/螺母判对的比例 |

**P 和 R 通常互相拉扯**：把阈值调低，能检出更多（R↑）但误检也会多（P↓）；调高反之。所以要看 F1。

## 5.4 我们项目的实测数字怎么读

```
图片数 40   命中 205   误检 26   漏检 78
精确率 P = 0.887      召回率 R = 0.724      F1 = 0.798
分类准确率 = 96.6%     检测耗时 = 2~3 ms/张
```

- **P=0.887**：**看到的框基本都可信**（9 个框里 8 个是真的）
- **R=0.724**：**每 4 个零件大约有 1 个没框到** —— 这是现在的短板
- **分类 96.6%**：框一旦对上，螺丝/螺母基本判对

**为什么 R 只有 0.72**（也是要讲给面试官听的）：
1. 两个零件挨在一起 → 闭运算把它们粘成一块 → 一个区域对两个标注 → 两个都算漏检
2. 强高光把零件切成碎片，剩下的部分面积不够或与标注框重叠太少（IoU < 0.5）
3. 改进方向：**距离变换 + 分水岭**拆分粘连；按类零件的尺寸先验做二次校验；加 ROI 缩小搜索范围

# 第 6 节 视觉里的"敌人"和对应的武器

| 敌人 | 现象 | 武器（硬件） | 武器（算法） |
|---|---|---|---|
| **镜面反光/高光** | 金属表面一块死白，阈值切开 | 漫射光、偏振片、环形光/穹顶光 | 闭运算补缝、局部阈值、换用边缘特征 |
| **阴影** | 工件旁边一圈暗，被误当工件 | 多角度打光、背光 | 面积/形状筛选、ROI |
| **光照不均** | 左边亮右边暗，一个阈值切不全 | 均匀光源 | `dyn_threshold`（局部阈值）、分块阈值 |
| **粘连** | 两个零件贴在一起算成一个 | 摆件时分开 | **分水岭（watershed）**、距离变换、模板匹配 |
| **噪声** | 图上很多小白点 | 提高曝光/增益 | 开运算、中值滤波 `median_image` |
| **对比度不足** | 工件和背景差不多亮 | 换光源/换角度 | `emphasize`（增强对比度）、换特征（边缘/纹理） |
| **背景杂乱** | 背景里也有类似亮度的东西 | 用白/黑背景板 | **ROI**、模板匹配 |

**我们这个项目的情况**：白盘子 + 固定机位 → 背景很干净，所以"背景杂乱"不成问题；
主要敌人是**反光（螺丝的高光）**和**粘连**。

> 💡 **分水岭（watershed）直觉**：把区域想象成地形，亮的地方是山、暗的地方是谷。
> 往地形上灌水，水会从各个"盆地"（每个零件的中心）同时上涨，涨到两个盆地相遇的地方就画一条分界线
> → 就把粘在一起的两个零件分开了。实现上通常先 `distance_transform`（算每个像素离背景多远）再灌水。

# 第 7 节 传统视觉 vs 深度学习

| | 传统视觉（我们这套） | 深度学习 |
|---|---|---|
| 怎么工作 | 人设计规则：阈值 → 形态学 → 特征 → 分类 | 从大量标注里自己学特征 |
| 数据量 | 几张~几十张就能调参 | 通常几百~几万张 |
| 可解释性 | **强**（能说清"因为长宽比 1.42 落在未知区所以判 NG"） | 弱（黑盒） |
| 速度 | 很快（我们 2~3 ms/张，CPU 就够） | 慢，通常要 GPU |
| 硬件成本 | 低 | 高（GPU、更多存储） |
| 擅长 | 形状规则、背景干净、目标少 | 形状多变、遮挡、堆叠、缺陷纹理 |

**我们为什么选传统**：
1. 形状差别大（螺丝长宽比 2.4 vs 螺母 1.07），规则特征就够了，实测分类 96.6%
2. 工业现场部署简单（不要 GPU、不要训练流程、license 便宜）
3. 可解释：出问题能定位到"是阈值不对还是粘连"

**什么时候该换深度学习**：零件种类变多（几十类）、互相遮挡堆叠、要做表面缺陷检测（划痕/脏污）。
那时才值得上训练流程。

# 第 9 节 我们项目里那些"反直觉决定"的来龙去脉

把整个项目里所有"为什么这么定"串一遍，这些就是面试时最值钱的内容：

| 决定 | 直觉上会怎么做 | 我们为什么反过来 | 证据 |
|---|---|---|---|
| **不用自动阈值** | "自动的多省事" | 直方图不双峰（金属高光），自动切出来全是碎片 | 自动 F1=0.270 vs 手动 120 F1=0.798 |
| **加闭运算** | 形态学会"改变形状" | 高光把零件切碎，必须连回来 | 半径 5 → F1 0.798；半径 6 → 0.787（粘连） |
| **不开运算** | 教科书说开运算去噪声 | 螺丝细长，开运算啃掉两端，特征全变 | 早期实测 F1 下降 |
| **用 rect2 不用 rect1** | 水平框多简单 | 水平框会把斜放零件量成方形，分类就废了 | 斜放零件：rect1≈1.2 vs rect2=2.4 |
| **分类阈值取 1.3/1.5** | 拍脑袋取 2.0 | 实测螺丝中位 2.40（10% 分位 1.46）、螺母 1.07（90% 分位 1.14） | 阈值落在两个分布中间 |
| **留"存疑"这一类** | 非黑即白分两类 | 卡在中间的硬分会制造错误，不如交给人工 | 1.3~1.5 之间判存疑（红框） |
| **OK/NG 只看置信度** | 用数量对不对判断 | 数量波动大且不反映"判得准不准"；置信度直接反映把握 | 架构决策（第 4.7 节） |
| **评估用 IoU≥0.5** | 中心落框就算命中 | 中心落框太松，粘连的大块也能"命中" | 换成 IoU 后 F1 从虚高 0.88 → 真实 0.27（当时）|
| **显示比例自己算 part** | 控件自带 `HKeepAspectRatio` | 它只在控件尺寸变化时生效，初次显示会拉伸 | 实测 1.88/2.20（错）→ 自算后 1.334（对） |

# 第 11 节 面试速答（把术语串成人话）

**"你这套检测怎么做的？"**
> 用的是传统视觉的经典链路：转灰度 → 手动阈值二值化 → 闭运算 → 连通域 → 面积过滤 → 用最小外接矩形的长宽比做分类。分类特征不是拍脑袋定的，我先用数据集自带的标注统计了形状：螺丝长宽比中位 2.40、螺母 1.07，所以阈值取 1.5 / 1.3，中间地带判"存疑"；置信度设计成"离边界多远"，方便上层把不确定的图判成 NG 交人工复核。

**"参数怎么调出来的？"**
> 写了个评估脚本，用 IoU ≥ 0.5 严格匹配算 P/R/F1，然后扫参数。两个反直觉的发现：HALCON 的自动阈值在这批图上很差（F1 0.27），因为它假设直方图双峰，而金属件高光破坏了双峰性，切出来全是碎片；换成手动阈值 120 后 F1 到 0.79。另外闭运算是必需的，半径 5 能把被高光切断的碎片连回来，但再大就会把相邻零件粘一起、召回率反而下降。

**"正确率多少？"**
> 精确率 0.887、召回率 0.724、F1 0.798、分类准确率 96.6%，单张 2~3 ms。现在的短板是召回率——约四分之一的零件漏检，主要来自粘连和强反光；改进方向是距离变换+分水岭拆分粘连、加 ROI、用零件尺寸先验做二次校验。

**"为什么不用深度学习？"**
> 三个原因：① 形状规则、背景干净，传统特征就够了（分类 96.6%）；② 现场部署要 GPU 和训练流程，成本和维护都高；③ 可解释——出问题我能定位到"阈值不对"还是"粘连"，黑盒模型做不到。如果以后零件种类变多、出现遮挡堆叠或要做表面缺陷检测，会考虑上深度学习。
